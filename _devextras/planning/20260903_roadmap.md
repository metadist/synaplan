# Roadmap 2026-09 — "more of the platform, self-service and governed"

**Status:** Draft 2026-09-03. Reference document for six planning tracks. Each
track has its own directory with a `00_master_plan.md` (decision checklist,
architecture, invariants, sprints) and a `STATUS.md`. **Nothing in the tracks
is decided until the checklist rows in the respective master plan are ticked.**
The tracks are discussed one at a time, in the order below.
**Origin:** a structured feedback review from an integration partner
(September 2026). The feedback is anonymized here; only the substance is kept.
**Owner:** product owner. Track owners are assigned when a track starts.

---

## 1. The feedback, in one paragraph

Synaplan is already a strong AI platform: DAG orchestration, many channels
(web, widgets, WhatsApp, email, Nextcloud, OpenCloud, ownCloud.online), RAG and
file handling, provider and model management, conversation memory, native
document generation. The main opportunity is not another capability. It is to
make the existing power **self-service, reusable, and governed** — so that an
organization can build a catalog of purpose-built AI experiences from the
same models, hand them to the right people, and keep control over what the
AI is allowed to do. Six work areas were named: enterprise permissions and
privacy, a reusable agent builder, pluggable AI infrastructure, custom tools
with human approval and a workflow builder, a secure compute workspace for the
AI, and linking Nextcloud to an existing Synaplan account.

The partner's priority reading was: foundation = agent builder + groups /
permissions + multiple OpenAI-compatible connections; high priority = secure
compute, Nextcloud account linking, pluggable extraction and search, tool
extensibility with approval; differentiators = customer-configurable workflows
and cross-channel orchestration.

We accept the substance and **change the order** (see §3): identity and
access is the foundation everything else attaches to, so it goes first.

## 3. Order and dependencies

```text
 1 IAM ──────────────┬──────────────┬──────────────┐
                     │              │              │
                     ▼              │              ▼
 2 Agent Builder ────┼───────┐      │      6 More Nextcloud
                     │       │      │        (identity table from IAM S1;
 3 AI Plugs ─────────┘       │      │         otherwise independent)
   (independent of 1/2;      ▼      │
    parallelizable)   4 Tools, Approval & Workflows
                             │
                             ▼
                      5 Secure Compute
                        (sidecar can start as a spike any time;
                         Synaplan integration needs 4's approval policy)
```

**Why IAM first.** Every later track asks "who may use this?": a published
assistant, a shared knowledge folder, an approval policy for a group, a
compute quota per team, a Nextcloud user linked to an account. Building those
without a shared answer means five ad-hoc permission models. IAM defines the
one answer (owner, group, share, permission) and ships an MVP that is useful
on its own: share a chat with its files, or a knowledge folder, with a group.

**Why the agent builder second.** It is the visible product the partner
described ("a catalog of purpose-built AI experiences from the same models").
It turns `BPROMPTS` + model bindings + knowledge + tools into one publishable
unit and uses IAM to publish. Everything after it (tools, approvals, compute)
attaches to an agent definition.

**Why plugs third.** Pure platform hygiene with immediate value (Docling,
SearXNG, rerank, model import). It has no dependency on 1 or 2 and can run in
parallel with them if capacity allows — it is third only because the first
two need the product owner's attention more.

**Then the rest.** Tools & approval need agents (policies live on agents and
groups). Compute needs the approval policy (running code is a write-class
action). Nextcloud linking needs only the identity table from IAM sprint 1
and is otherwise a small, independent track that can be pulled forward when a
hoster asks for it.

### 3.1 Waves (what can run at the same time)

| Wave | Tracks | Exit criterion |
| ---- | ------ | -------------- |
| W1 | 1 IAM (S0–S2) — optionally 3 AI Plugs S1 in parallel | Groups exist; a knowledge folder and a conversation can be shared with a group; nothing changes for installs without groups |
| W2 | 1 IAM (S3–S4), 2 Agent Builder (S1–S3), 6 More Nextcloud (S1) | An admin publishes an assistant to a group; OIDC groups sync; a Nextcloud user links an existing account |
| W3 | 3 AI Plugs (S2–S5), 2 Agent Builder (S4–S6), 6 More Nextcloud (S2–S3) | Docling + SearXNG + rerank selectable; assistants carry knowledge, tools and tasks |
| W4 | 4 Tools, Approval & Workflows (S1–S4), 5 Secure Compute (S0–S2) | Write-class tools require approval, also in unattended runs; the compute sidecar runs hostile-script corpus green |
| W5 | 4 (S5–S6), 5 (S3–S5) | Workflow builder v1; compute integrated into agents and tools with quotas and audit |

Waves are a capacity plan, not a promise. A wave ends when its exit criterion
is met, not when the calendar says so.

## 4. Principles that bind all six tracks

These are the house rules applied to this roadmap. Each master plan repeats
the ones that matter most for it as named compatibility invariants.

1. **Ports and adapters, not monoliths.** A new capability is a PHP interface
   (the port) plus a registry (`#[AutowireIterator('app.<area>.<kind>')]`,
   the pattern `RunnerRegistry` / `DestinationRegistry` / `ProviderRegistry`
   already use) plus adapters. Adapters are small. Plugins may contribute
   adapters through manifest v2 `provides.*` (open-plugin-platform plan).
2. **Sidecars where the ecosystem is not PHP or the risk is process-level.**
   Docling is Python; SearXNG is its own image; running AI-authored code
   needs a container boundary. Those live in their own containers behind a
   small, versioned HTTP contract with a health endpoint and an opt-in
   compose profile. PHP holds a thin client and never mounts a Docker
   socket. Precedents: Tika, `synaplan-tts` (Piper), Collabora, the Go
   backend in `synaplan-opencloud`. A Go or Rust sidecar is preferred over
   PHP when it needs Docker/containerd APIs, long-running processes, or
   streaming of process output.
3. **Default off, additive, reversible.** Every track ships behind a
   `BCONFIG` flag that defaults off in code and in the seeder until the
   track's success criteria are met. Migrations are Galera-safe
   (`addSql` only, `IF NOT EXISTS`, no `Schema` API; see `docs/MIGRATIONS.md`).
   Rollback is "flag off"; data stays.
4. **Regression is a first-class deliverable.** Each sprint names the
   invariants it must not break and the tests that prove it: routing
   characterization snapshots stay untouched unless the sprint says so;
   CORE-5 knowledge isolation holds; OIDC login, API-key scopes, widget,
   mobile and the `/v1` gateways stay byte-identical. A refactor sprint
   ("wrap the existing thing in the new port") always precedes a feature
   sprint on the same seam.
5. **Growth plans, not big bangs.** Each master plan has a v1 that is
   useful alone, a named cut line, and a "v2 and later" section. Steps are
   PR-sized (one concern, one PR), tracked in the track's `STATUS.md`.
6. **Explainable to a non-technical user.** Each track starts with a
   three-sentence concept and a canonical vocabulary in all five locales
   (`en`, `de`, `es`, `fr`, `tr`). Navigation stays as lean as it is today
   (`useNavItems.ts`): new surfaces are children of existing sections or
   replace an existing child; no new top-level rail item without a decision
   row.
7. **Security posture never regresses.** Owner always wins; admin power is
   separated from access to private content; every write-class action has a
   policy; every cross-user access, approval, impersonation and compute run
   is audited.
8. **Mobile app compatibility.** Every change is classified
   (`backend-only` / `ota-candidate` / `store-required`) in the same PR, with
   new paths added to the allow-lists in `.github/mobile-impact-policy.json`.

## 6. Cross-track vocabulary (binding once ticked in track 1)

| Term (en) | Meaning | Not to be confused with |
| --------- | ------- | ----------------------- |
| **Owner** | The one person a resource belongs to. Never changes by sharing. | Admin |
| **Group** | A named list of people. Manual or synced from the company login. | `BCONFIG.BGROUP` (config namespace), `BGROUPKEY` (knowledge folder key), billing tier `TEAM` |
| **Share** | A grant of *read*, *use*, *edit* or *manage* on one resource to a user, a group or everyone | Public link |
| **Assistant** | A published, versioned bundle of instructions + models + knowledge + tools + skills + parameters (+ tasks). Code name `agent`. | "AI Agents" nav item (`/channels/agents`, the Messages gateway) — renamed in track 2 |
| **Tool** | One callable action with a side-effect class (`read` / `write` / `destructive`) | Skill (a DAG building block), Command (`/slash`) |
| **Plug** | A capability slot with interchangeable providers (extraction, web search, rerank) | Plugin (a packaging unit), Provider (an AI vendor) |
| **Approval** | A pending decision on a write-class action, interactive or in an inbox | Human takeover (widget live support) |
| **Workspace (compute)** | A per-user or per-run sandbox directory managed by the compute sidecar | The nav "workspace" seam in `useNavItems.ts` |

Translations for all five locales are fixed in each track's UX section before
the first UI PR.

## 7. How a track is executed

1. Discuss and tick the decision checklist in `00_master_plan.md` §0. A
   rejected row is rewritten in the same change with the alternative.
2. Write the sprint files (`01_sprint_1_*.md` …) and the work breakdown with
   PR-sized steps, following the format of
   [`20260829-desktop-agent-client/`](./20260829-desktop-agent-client/).
3. First PR of every seam is the **refactor sprint**: wrap what exists in the
   new port, behavior identical, gate green, snapshots untouched.
4. Every PR: feature branch, Conventional Commit type that matches the
   release impact (`feat` raises the minor version), full pre-commit gate,
   mobile-impact classification, five locales.
5. `STATUS.md` in the track directory is the single place for step state and
   decisions; this roadmap only links to it.
6. When a track ships its v1, its directory moves to `2026-archive/` with a
   closing note, and this file's table gets a "shipped in vX.Y" column entry.
