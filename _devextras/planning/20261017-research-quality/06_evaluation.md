# Evaluation — how we know research got better

**Status:** Draft 2026-10-17. Built in RQ2, used by every RS step and by the
bake-off RQ3. The question this answers for the owner: *does Synaplan now
research as well as a strong IDE agent — and does the model team beat a single
model at a lower cost?* Only numbers from the commands below count.

---

## 1. Principles

1. **The production path is the test subject.** The engine is evaluated
   through `ResearchRunService`; today's web chat through the services the stream
   uses; today's Desktop through the desktop runner on its production core. No
   re-implementation of a path for the test.
2. **Fixed corpus, planted facts, traps.** Gold facts are checked by a person
   when an item is written; items whose facts age carry `valid_until` and are
   refreshed quarterly.
3. **Deterministic where possible.** Quote integrity, citation resolution,
   terminal states, cost and time need no model.
4. **Judges from other families, blind, calibrated.** A model never judges its
   own family's output; judges do not see which arm wrote a report; judge
   agreement with people is measured before a judge number gates anything.
5. **Numbers only from commands**, recorded in STATUS with the command and the
   corpus version.
6. **No customer data.** Web items use public sources; document items use a
   synthetic corpus generated by a script.
7. **Borrow, do not reinvent, the public yardsticks.** The metrics map onto
   DeepResearch Bench (RACE for report quality, FACT for citation
   trustworthiness), and the `--frozen` replay follows BrowseComp-Plus (a
   fixed corpus with supporting and hard-negative documents so retrieval and
   the model can be measured apart). A handful of public DeepResearch Bench
   tasks may be added to the corpus as an outside reference; they never gate.

## 2. The corpus (RQ2)

`backend/tests/Eval/research/corpus.json` (items),
`backend/tests/Eval/research/documents/` (synthetic files, generated
deterministically by a script in the same folder), `judges/` (judge prompts).
Not part of the PHPUnit gate (live models cost money), like the sort eval.

### 2.1 Mix — 40 items

| Category | Items | Languages | What it tests |
| -------- | ----- | --------- | ------------- |
| Current facts | 5 | en, de | Freshness, official sources |
| Comparison | 5 | en, de, fr | Table output, coverage across items, vendor sources used correctly |
| Regulation and law (DE / EU) | 5 | de, en | Official sources, PDFs, exact article references |
| Technical documentation | 5 | en | Precision, documentation over blogs |
| Science | 4 | en | Papers and PDFs, careful claims |
| Local and market | 4 | es, fr, tr, de | Queries in the local language |
| Own documents only (Web off) | 6 | de, en | Knowledge search, multi-document answers, planted facts, file citations |
| Web + own documents | 3 | de, en | Combining both, citing both kinds |
| Traps | 3 | en, de | A non-existent law (must abstain), an outdated fact (must use the current one), conflicting sources (must show both) |

Smoke set: 10 items (one or two per category, one trap). Full set: 40.

**Build order.** RQ2 ships a **starter set of 20 items** (the smoke set plus
ten more, every category covered) with B0 first, because early changes have
large effects that a small set already shows. The remaining 20 items and the
human calibration of §4 follow before RQ3; no flag decision is taken on the
starter set.

### 2.2 Item format

```json
{
  "id": "reg-03",
  "category": "regulation",
  "language": "de",
  "question": "Welche Pflichten gelten seit 2026 für Anbieter von KI-Modellen mit allgemeinem Verwendungszweck nach der EU-KI-Verordnung?",
  "depth": "standard",
  "sources": { "web": true, "knowledge": false },
  "gold": [
    { "id": "g1", "assertion": "…", "kind": "fact", "match": ["Art. 53"] },
    { "id": "g2", "assertion": "…", "kind": "fact" }
  ],
  "preferred_sources": ["eur-lex.europa.eu", "digital-strategy.ec.europa.eu"],
  "time_frame": { "from": "2025-08-01" },
  "trap": null,
  "valid_until": "2027-01-31",
  "written_by": "initials",
  "checked_on": "2026-10-xx"
}
```

Document items reference planted facts by file and location (for example
"Rahmenvertrag_A.pdf, page 7: notice period three months"), like the use-case
runner's UC-06 corpus.

## 3. Metrics

| Metric | Definition | How |
| ------ | ---------- | --- |
| **Fact recall** | Share of gold assertions the report states | Match strings first (numbers, names), then two judges per assertion: present / absent / contradicted |
| **Contradiction rate** | Share of gold assertions the report contradicts | Same judgement |
| **Citation precision** | Share of cited statements whose cited quotes support them | Two judges (other families than the checker), human sample of 10 % |
| **Citation coverage** | Share of factual sentences with a citation | Deterministic flagging (numbers, dates, names) + judge for the rest |
| **Passage integrity** | Share of cited passages that exist and whose quote, when present, is inside them | Deterministic; must be 100 % — it tests the passage check itself |
| **Dropped findings** | Share of reader findings dropped by the passage check, per reader model | Deterministic; high values mean the reader invents locations — a reader selection signal for RQ3 stage 1 |
| **Search efficiency** | Searches and sources read per covered point; repeated or near-duplicate queries | Deterministic from the ledger; compares tool mode with round mode |
| **Abstention** | Trap and unanswerable items answered with "not confirmed" instead of a claim | Judge + rule (no gold-contradicting claim) |
| **Source quality** | Share of citations from official, primary, academic or documentation sources where the category requires them | Triage classes + `preferred_sources` |
| **Freshness** | Time-sensitive assertions supported by sources inside the time frame | Source `published` dates |
| **Plan coverage** | Do the plan's points cover the question's aspects (1–5) | Judge rubric |
| **Readability** | Structure, plainness for the audience, language correctness in the target locale (1–5) | Judge rubric; native-speaker sample for de, es, fr, tr |
| **Cost per run** | Sum of the run's usage records | `BUSELOG`, source `RESEARCH` |
| **Time** | p50 / p95 from start to `complete` | Event timestamps |
| **Terminal state** | Runs that end in `complete`, `stopped` or `failed` with an outcome code | Deterministic; a run still `gathering` 60 s past its wall clock fails the gate |

## 4. Judges

- **Pair:** two judges from families other than the arm's writer and checker
  (for a Claude writer and a Gemini checker: GPT-6.1 Sol and Grok 4.7, for
  example). A disagreement goes to a third judge; still split → "uncertain",
  counted separately and sampled by a person.
- **Blind:** arm names removed, report order shuffled.
- **Calibration (RQ2):** two people label 40 assertion–report pairs and 40
  statement–quote pairs. A judge's agreement with them (Cohen's κ) is recorded
  in STATUS; a judge below κ 0.7 is not used for gates.
- **Versioned:** judge prompts in `backend/tests/Eval/research/judges/`, changed
  only with a recalibration.

## 5. Baselines and targets

| Arm | What it is | Produced by |
| --- | ---------- | ----------- |
| **B0** | Today's web chat with web search on (classifier → search → read 3 pages → one answer); knowledge items through the chat's knowledge loader | `app:research:eval --arm=b0` |
| **B1** | Today's Desktop agent turn with Web on and the knowledge folder header | The desktop runner (`usecases --research-corpus`), scored by the same scorer |
| **B1+** | Today's gateway tool loop **after Phase B** (RS1–RS3): a frontier model with `web_search`, `web_fetch` and `knowledge_search`, `WEB_SEARCH_MAX_ROUNDS` raised to 6 and a research system prompt — the model-driven path we already own, and the engine's strongest cheap competitor | `--arm=b1plus` (through `/v1/messages` with an eval key) |
| **B2** | The engine with one model (the lead's) in every role | `--arm=b2` |
| **B3** | The engine with the team (a preset) | `--arm=preset:<world>.<depth>` |
| **B4** | An external deep-research agent as a reference point (for example the Gemini Deep Research agent on the Interactions API, about 1–3 USD per task) — eval only, its report scored by the same scorer; its citations are mapped to URLs and checked by the judges | `--arm=b4:<agent>`; needs the provider key and is never a gate for CI |
| **S-R / S-T** | The spike (RQ2b) in round mode and in tool mode | `app:research:spike --mode=rounds|tools`, scored by the same scorer |

**The go / no-go gate before Phase C (§0 #40)** compares S-R and S-T with
B1+ on the frozen starter set: go when the better spike arm beats B1+ by
≥ 10 points on fact recall, or reaches the citation-precision target below
where B1+ does not, at no more than twice B1+'s cost. B4 is reported next to
them so the owner sees where "good" lies, but it does not decide the gate.

**Targets — the gate for seeding `RESEARCH.ENABLED` on (§0 #19, #23):**

| Metric | Standard | Thorough |
| ------ | -------- | -------- |
| Fact recall | ≥ B0 + 15 points | ≥ B0 + 25 points |
| Citation precision | ≥ 92 % | ≥ 95 % |
| Citation coverage | ≥ 90 % | ≥ 95 % |
| Passage integrity | 100 % | 100 % |
| Fact recall vs B1+ | ≥ B1+ + 10 points | ≥ B1+ + 15 points |
| Abstention on traps | ≥ 2 of 3 | 3 of 3 |
| Contradiction rate | ≤ 3 % | ≤ 2 % |
| Time p50 / p95 | ≤ 3 / 6 min | ≤ 12 / 20 min |
| Cost p50 (catalog currency) | ≤ 0.60 | ≤ 3.00 |
| Terminal state | 100 % | 100 % |
| Team vs single model (B3 vs B2) | within 2 points on recall and precision, at least 30 % cheaper | same |

The targets are proposals; RQ2's baseline may move the relative ones before
RS6 starts — a change is a dated STATUS row, not a silent edit.

## 6. Harness

```bash
docker compose exec -T backend php bin/console app:research:eval \
  --corpus=smoke                       # smoke | full | path to a corpus file
  --arm=preset:cloud.standard          # b0 | b2 | b3 | preset:<world>.<depth> | models:lead=…,reader=…,checker=…
  --judges=openai:gpt-6.1-sol:chat,xai:grok-4.7:chat
  --frozen=var/research-eval/frozen/2026-11-02   # replay recorded searches and sources (bake-off stages 2+)
  --repeat=2                           # noise estimate
  --report=var/research-eval/2026-11-02-cloud-standard.md
```

- Runs under an internal evaluation account; writes usage records there and
  nothing else.
- Writes a Markdown report (per item, per metric, aggregates, cost, time) and a
  JSON summary that STATUS rows are copied from.
- `--frozen` records search results and fetched source texts on the first run
  and replays them afterwards, so model comparisons are not confounded by a
  changing web.

**Noise band.** On the smoke set, a difference under 3 points between two arms
is noise unless it repeats over `--repeat=2`. Gates are decided on the full
set.

**PR rule (RS1–RS10, prompt changes).** The PR description carries a smoke run
of the changed path; it must not be worse than the last STATUS smoke row beyond
the noise band. A regression needs a STATUS note accepted by the owner.

**Budget.** A full Standard arm costs roughly 15–20 in catalog currency
including judges; Thorough on ten items about 25; the whole bake-off about 250.
The owner approves the RQ3 budget before it runs.

**STATUS row format:**

| Date | Step | Arm | Corpus | Depth | Recall | Citation precision | Coverage | Abstention | Cost p50 | Time p50 / p95 | Command |
| ---- | ---- | --- | ------ | ----- | ------ | ------------------ | -------- | ---------- | -------- | -------------- | ------- |

## 8. What runs in CI, and with what

CI never reaches the live web or a provider (§0 #27). The doubles:

| Double | Replaces | Lives | Fixtures |
| ------ | -------- | ----- | -------- |
| `TestWebSearchAdapter` | the web search provider | `test` env, or `WEB_SEARCH.PROVIDER = test` | `backend/tests/Fixtures/research/search/<slug>.json` — query → results with `https://fixture.synaplan.test/<page>` URLs |
| `FixtureSourceReader` | `ResearchSourceReader` | `test` env | `backend/tests/Fixtures/research/pages/<page>.html|.pdf` — served without a network call; any other host is "blocked: not a fixture" |
| `TestProvider` mocks | the `tools:research_*` prompts, including scripted tool-call turns for `tools:research_lead` | always (it is the test provider) | schema-aware canned answers keyed by the prompt topic and by markers in the question (the `websearch:` prefix pattern of `multitask.spec.ts`) |

**Execution in the test environment.** The test stack runs no Messenger
worker: `when@test` in `backend/config/packages/messenger.yaml` maps every
transport to `in-memory://` and routes the commands Playwright must see to a
`sync://` transport (`ExtractMemoriesCommand`, the Telegram commands).
`RunResearchUnit` gets the same treatment: in `test` it is routed to `sync`,
so a start request executes the unit chain inline until the run completes or
reaches a waiting state, and an `input` request continues it inline. The
`DelayStamp` between units is ignored by the sync transport. PHPUnit tests
that need a *pause* between units (resume after a killed worker, the claim
race, the sweeper) use the in-memory transport and pull messages from it one
by one with `InMemoryTransport::get()`, so both behaviours are covered without
a worker process.

With these, PHPUnit replays whole runs (every stage, every outcome, the
injection page, five languages, erasure, the sweeper, idempotency, the claim
race) and Playwright walks J-RQ-8 as an `@ci` journey whose report appears in
the chat because `deliver` writes it server-side (`03` §2.8). The SSRF guard is
never relaxed; a test that wants a real page or a real key is an eval or a
desktop quick-set case, not a gate test.
