Synaplan after the architecture update

One product, four spines, and a runtime that holds the model’s stream so a PHP worker does not. This is the target once sprints S0 through S6 have landed. Agentic research, which arrived while the plan was in progress, joins this shape. It does not replace it.

How this path moves

  1. The person sends a message from the web app, the widget, the desktop or mobile app, or an SDK.
  2. Caddy hands that long route to the watchdog. If every stream slot is taken, the reply is “busy — your message was not sent,” and the client retries.
  3. The watchdog asks PHP to prepare the turn: who is asking, which model, history, retrieved files and memories, and the prompt. PHP enqueues a job that names the run and carries no provider key, then steps aside.
  4. The watchdog keeps the browser connection and reads frames from the run’s Redis stream. A keep-alive goes out during silence. The stream always ends on a terminal frame.
  5. A pump process opens the provider socket through the one pipeline and the one HTTP client. Each chunk is decoded into the same server-sent events the apps already understand.
  6. A tool call leaves the pump. A worker runs the invoker: look up the tool, apply the approval gate, execute, clamp the result, audit a write, record usage, then queue the next model round.
  7. When the model finishes, a worker stores the reply, closes the single usage row for the turn, and queues memory extraction.
  8. If the page drops, it re-attaches with a signed cursor and continues from the last frame. A web restart drops the connection. The answer keeps going.
  1. The upload arrives on the API pool. It never takes a stream slot.
  2. Tika extracts a document, Whisper a recording. An embedding call goes through the same pipeline as chat, labelled as vectorize, so it is metered and visible.
  3. The vectors live in MariaDB, and in Qdrant when that store is on. The file itself stays on disk, with its row in MariaDB.
  4. A later chat prepares its turn by searching those vectors. The passages go into the prompt. This plan does not change how the prompt is assembled.
  5. From there the answer follows the streamed path: watchdog, pump, pipeline, and the same server-sent events.
  1. Mail, WhatsApp, and Telegram still arrive as webhooks on the API pool. Intake, deduplication, and the stored message stay as they are.
  2. The turn is buffered. PHP waits for the whole answer, then sends the mail or the WhatsApp message. These routes are not held by the watchdog.
  3. The model call is still one AiCall. The same hooks, the same meter, and the same outbound client apply.
  4. A tool inside that turn uses the same invoker as a chat tool, including the approval gate and the audit row for a write.

Plan targets, not production counts. The stream figure is the acceptance budget: 500 streams of 10 seconds with none failed. The spike held 1,000 provider streams in one PHP process at about 134 MB, and 2,000 client connections in the Go relay.

One door for every model call

Chat, the widget, both public APIs, the sorter, embeddings, memory, rerank, probes, and live-voice usage enter through AiFacade and leave through AiCallPipeline. Ordered hooks apply the rate limit and the circuit breaker before the call, then record health, usage, and metrics after it. The pipeline’s own overhead stays under 1 ms at the 95th percentile. Each billable turn has exactly one usage row.

A provider is one class

descriptor() states capabilities, endpoints, keys, dialects, and the icon. The catalog is what keys, the allowlist, pricing, and the admin screen ask. The browser reads names and icons from GET /api/v1/ai/providers. An OpenAI-compatible provider is that class plus its model rows.

One way out, and one tool gate

EgressHttpClient is the HTTP stack: the enterprise proxy, an allowlist built from enabled providers and configured integrations, and a check on every redirect. A URL a person typed stays pinned to the address that was checked. MariaDB, Redis, mail, and Triton gRPC are listed rather than forced through that client. An optional CONNECT gateway covers PHP, voice, the transcriber, and compute. Every tool loop calls ToolInvoker. The approval gate always runs. A write lands in the audit log. A read becomes a metric. Edits to the person’s own files stay automatic.

PHP stops waiting on the model

The watchdog holds the client. A few pump processes hold the provider sockets. Workers run tools and save the reply. A full server answers at once, and the API pool stays fast while streams are saturated. Kubernetes probes follow that capacity, and autoscaling watches held streams. Turning the watchdog or the pump off puts streams back in the PHP pool.

The wire, the prompt, and the live channel stay

Server-sent event names and payloads do not change, so the web app, the widget, desktop, and the mobile apps keep their readers. Prompt assembly, Centrifugo, Messenger, and the scheduler stay. Mail and WhatsApp keep their adapters. Only their model calls join the pipeline. Plugins beyond a one-file provider wait for a later track.

Agentic research still fits

From 24 October through 28 October 2026 the research engine landed on main: a lead model that calls search, read_sources, reread, ask_user, and finish, running as Messenger units. Research mode is in the web chat, on AI infrastructure, and as a Saved Task step. The switch stays off. Notion page edits landed in the same window, inside the existing McpActionRunner, which the tool sprint already lists.

The spines still hold

The lead, the reader, the writer, and the fact-checker all call AiFacade::chat(). That method now runs AiCallPipeline. Research did not add a second way to a provider. The cost figure it keeps is the run’s own budget. It does not write a second usage row.

Starting a run queues a unit and returns. The watchdog, the two PHP pools, and the later stream pump remain about the browser’s open answer. A research round holds a Messenger worker for the time the run has left, plus four minutes. That is the same role the plan already gives tool steps, saving the reply, and memory extraction. Redis keys are research:*, separate from the capacity snapshots and from the future chatrun: stream.

Page fetches already use the guard the egress sprint relies on. UrlContentService checks the address with SsrfGuard before it connects. Provider endpoints and these model-chosen page addresses stay different kinds of destination.

Two inventories to update before those sprints

The tool sprint still names three loops: document chat, the Messages gateway, and the OpenAI gateway. There is now a fourth, LeadStage together with LeadToolbox. It applies the run’s own budget and does not call ToolExecutionGate. AU23 characterizes it with the others. AU24 can send those calls through the invoker as automatic reads. AU26 keeps unifying the three chat and gateway loops. The research loop pauses for a person’s answer and checkpoints between units, so folding it into that chat loop would drop the part that lets the run survive a closed tab.

When the egress allowlist is enforced, a research page fetch stays on the pinned-address path. An allowlist made only of provider hosts would refuse every source the lead opens, the moment an administrator turns research on.

One label is missing on the pipeline. A research chat() call does not name a channel, so today it is recorded as chat_web. A research source, added before the usage hook becomes the only writer, keeps those calls out of the chat quota and visible on the capacity page as their own kind of work.
